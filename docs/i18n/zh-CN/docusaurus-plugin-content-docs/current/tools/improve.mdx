## 概述 {#overview}

生成可执行的代码建议，用于改进拉取请求。
该工具可以在每次新拉取请求[打开](../usage-guide/automations_and_usage.md#github-app-automatic-tools-when-a-new-pr-is-opened)时自动触发，也可以在任意拉取请求上评论来手动调用：

```toml
/improve
```

## 使用示例

### 手动触发

在任意拉取请求上评论 `/improve` 来手动调用该工具。代码建议默认呈现为一条评论：

要编辑与 `improve` 工具相关的[配置](#configuration-options)，使用以下模板：

```toml
/improve --pr_code_suggestions.some_config1=... --pr_code_suggestions.some_config2=...
```

例如，可以运行以下命令，把替换范围已验证的建议呈现为可提交的代码评论：

```toml
/improve --pr_code_suggestions.committable_code_suggestions=true
```

替换范围无法验证的建议仍是普通评论，没有应用操作。

:::note
该键在 1.0 之前的拼写修正前写作 `commitable_code_suggestions`。该拼写仍然
可用，但已弃用：它会记录一条警告，并将在 1.0 中移除。请将其重命名为
`committable_code_suggestions`。
:::

如果批量发布失败，`/improve` 会逐条重试每条建议。如果每次重试都失败，
它会报告失败，而不是静默移除进度评论。当
`config.propagate_tool_errors=true` 时，发布错误也会抛给调用方。
普通回退评论和覆盖范围提示会在报告错误之前发布。
当此回退输出成功时，会予以保留，不再附加失败横幅；
错误传播仍遵循 `config.propagate_tool_errors`。
如果任何一次单独重试成功，则保留现有的部分恢复行为。

### 自动触发

要在拉取请求打开时自动运行 `improve`，在[配置文件](../usage-guide/configuration_options.md#local-configuration-file)中定义：

```toml
[github_app]
pr_commands = [
    "/improve",
    ...
]

[pr_code_suggestions]
num_code_suggestions_per_chunk = ...
...
```

- `pr_commands` 列出拉取请求打开时会自动执行的命令。
- `[pr_code_suggestions]` 节包含你想修改的 `improve` 工具配置（如果有）

### 增量建议

在 Azure DevOps 上，运行 `/improve -i` 只分析最近一次代码建议之后的变更。第一次
增量运行在不存在更早的建议评论时，会分析整个拉取请求。之后若没有新
变更，则退出且不调用模型。

### 表格与可提交代码评论

PR-Agent 支持两种呈现代码建议的模式：

1) [表格](pathname:///img/code_suggestions_as_comment_closed.png)模式

2) [行内可提交](pathname:///img/improve.png)代码评论模式。

表格格式有几个关键优势：

- **减少噪音**：拉取请求更干净，杂乱更少
- **快速概览和排优先级**：可以快速查看一行摘要、影响级别，并轻松排优先级
- **高层建议**：不绑定到特定代码块的高层建议只在表格模式中呈现
- **集中跟踪**：在一处显示建议的落实状态
- **IDE 集成**：可以通过 CLI 工具直接在 IDE 中应用建议

表格模式是 PR-Agent 的默认模式，由于这些好处，是大多数用户的推荐方式。

<img src="/img/code_suggestions_as_comment_closed.png" alt="code_suggestions_as_comment_closed.png" width="512" />

有特定偏好的团队可以在本地配置中启用可提交代码评论模式，或使用[双发布模式](#dual-publishing-mode)。

> `注意：由于平台限制，Bitbucket Cloud 和 Server 只支持可提交代码评论模式。`

## `附加指令`与`最佳实践` {#extra-instructions-and-best-practices}

可以通过向 AI 模型提供附加指令和最佳实践，进一步自定义 `improve` 工具。

### 附加指令 {#extra-instructions}

可以使用 `extra_instructions` 配置选项，为 `improve` 工具向 AI 模型提供附加指令。
指令要具体、清楚、简洁。使用附加指令时，你就是提示词的作者。

可能的指令示例：

```toml
[pr_code_suggestions]
extra_instructions="""\
(1) Answer in Japanese
(2) Don't suggest to add try-except block
(3) Ignore changes in toml files
...
"""
```

使用三引号编写多行指令。使用项目符号或编号让指令更易读。

### 最佳实践 {#best-practices}

`支持仓库上下文文件的平台：GitHub、GitLab、Gitea、Bitbucket、Azure DevOps`

开源 PR-Agent 包不会自动加载 `best_practices.md`。要使用最佳实践文件，
把它加入 `config.repo_context_files`：

```toml
[config]
repo_context_files = ["AGENTS.md", "best_practices.md"]
```

此回退支持 GitHub、GitLab、Gitea、Bitbucket 和 Azure DevOps。仓库上下文文件默认从默认分支读取，并受 `config.repo_context_max_lines` 限制（默认 500 行）。
设置 `config.repo_context_from_default_branch = false` 可改为从拉取请求的目标分支读取。
不支持获取仓库文件的提供方会记录警告并跳过此上下文。

<details>
<summary>编写有效的最佳实践文件</summary>

以下准则适用于所有最佳实践文件：

- 写得清楚、简洁
- 有帮助时包含简短代码示例，并采用修改前/修改后模式
- 聚焦项目特有的准则，以便得到你真正想要的相关建议
- 每个文件保持简短、聚焦，因为：
    - AI 模型可能无法有效处理很长的文档
    - 长文件往往包含 AI 已经知道的通用准则
    - `config.repo_context_max_lines` 限制渲染后的仓库上下文总量，包括包装行和截断行。
- 使用基于模式的结构，而不是简单项目符号，以便更清晰

</details>

<details>
<summary>最佳实践文件示例</summary>

模式 1：在外部函数调用周围添加带 try-except 块的适当错误处理。

修改前的示例代码：

```python
# Some code that might raise an exception
return process_pr_data(data)
```

修改后的示例代码：

```python
try:
    # Some code that might raise an exception
    return process_pr_data(data)
except Exception as e:
    logger.exception("Failed to process request", extra={"error": e})
```

模式 2：在访问对象属性或对可能为空的变量执行操作之前，添加防御性的空值/空检查，以防止运行时错误。

修改前的示例代码：

```python
def get_pr_code(pr_data):
    if "changed_code" in pr_data:
        return pr_data.get("changed_code", "")
    return ""
```

修改后的示例代码：

```python
def get_pr_code(pr_data):
    if pr_data is None:
        return ""
    if "changed_code" in pr_data:
        return pr_data.get("changed_code", "")
    return ""
```

</details>

### 结合 “extra instructions” 与 “best practices”

`extra instructions` 配置更贴近 `improve` 工具的提示词。例如，可以用它避免特定建议（"Don't suggest to add try-except block"、"Ignore changes in toml files" 等），或强调特定方面或格式（"Answer in Japanese"、"Give only short suggestions" 等）。

相比之下，`best_practices.md` 文件是仓库中代码应当如何编写的一般准则。

两者结合可以帮助 AI 模型提供相关且贴合的建议。

## 使用提示

### 落实所提议的代码建议

每条生成的建议包含三个关键要素：

1. 所提议变更的单行摘要
2. 可展开节，包含对该建议的全面描述
3. 展示建议代码修改的 diff 片段（修改前和修改后）

建议用户在落实所提议的建议时运用批判性分析和判断。
除了错误（可能发生，但很少见）之外，有时所呈现的代码修改更像是一个*说明性示例*，而不是可以直接应用的解决方案。
在这种情况下，建议优先考虑建议的详细描述，把 diff 片段主要当作辅助参考。

### 双发布模式 {#dual-publishing-mode}

我们推荐通过[表格](./improve.mdx#overview)呈现代码建议（`--pr_code_suggestions.committable_code_suggestions=false`）。
这种方法显著减小拉取请求占用，并能快速、轻松地消化多条建议。

我们还提供互补的**双发布模式**。启用后，超过某一分数阈值的建议不仅显示在表格中，也会作为可提交的拉取请求评论呈现。
此模式有助于突出被认为更关键的建议。

要激活双发布模式，使用以下设置：

```toml
[pr_code_suggestions]
dual_publishing_score_threshold = x
```

其中 x 表示除表格之外还要作为可提交拉取请求评论呈现的建议的最低分数阈值（>=）。默认值为 -1（禁用）。

### 持久行内评论

默认情况下，PR-Agent 会在每次运行时重新发布相同的行内代码评论，这会弄乱讨论，在 GitLab 上尤其如此。持久行内评论功能通过跳过重新发布更早运行中已经存在的评论来避免这一点。做法是在每条已发布评论中嵌入带短指纹的隐藏 HTML 注释标记，使 PR-Agent 能在后续运行中扫描已有评论正文，识别并跳过重复项。

使用两个指纹，并以 OR 逻辑匹配：一个覆盖评论文本（文件、行、规范化文本），另一个在存在时覆盖
所提议的代码块。即使模型改写了
正文或略微改动了代码，这种方法也能抓住再次发出的发现。该功能为可选，默认关闭，并已在 GitHub、
GitLab 和 Azure DevOps 提供方上实现。

Azure DevOps 指纹包含完整行范围和规范化的发现文本，因此另一处的相同问题仍然符合条件。当所提议代码与当前文件完全匹配时，活动建议讨论会被标为已修复。已有的终态会被保留。

GitLab 和 Azure DevOps 还会在下一次建议
流程中，把更早的建议讨论及其回复作为上下文。常规 `/improve` 会审查当前完整拉取请求，同时避开已经提出、
已处理、已拒绝或已推迟的问题。使用 `/improve -i` 只审查上一次建议流程之后的变更。
在 GitLab 上，每个讨论都带有状态：`open`、`auto_resolved`（由已认证的 PR-Agent 用户关闭，例如
通过 `resolve_outdated_inline_threads` 或 `auto_resolve_fixed_inline_threads`，因此发现可能仍然
适用）、`resolved`（由其他人关闭，或无法验证 PR-Agent 用户时）或 `applied`（建议
已通过 GitLab UI 应用）。

重复抑制和已应用建议的核对需要 `persistent_inline_comments`。讨论上下文
和线程问题在没有它时仍然可用。

要启用它，使用以下设置：

```toml
[config]
persistent_inline_comments = true
```

### 在 GitLab 上批量发布可提交建议

`支持的平台：GitLab`

默认情况下，启用 `committable_code_suggestions` 时，GitLab 会在每条建议创建后立即将其作为自己的实时讨论发布，这意味着每条建议都会有单独的通知（如果已配置，还有邮件）。要改为把所有建议排队，并在单次批量中一起发布，类似于在 GitLab UI 中使用 “start a review”，请启用：

```toml
[gitlab]
publish_code_suggestions_as_review = true
```

建议会作为 GitLab 草稿笔记发布（发布前只有 PR-Agent 的用户可见），并在所有建议排队后通过一次 API 调用一起发布。无论哪种方式，建议都完全可提交——此设置只改变投递方式。只有至少有一条建议实际入队时才会发起发布调用，因此一次没有内容可发布的运行不会意外发布 MR 上已待处理的无关草稿。

### 自审

`支持的平台：GitHub、GitLab`

如果在配置文件中设置：

```toml
[pr_code_suggestions]
demand_code_suggestions_self_review = true
```

`improve` 工具会在建议下方添加一个复选框，提示用户确认已审阅这些建议。
可以通过以下方式设置复选框文本内容：

```toml
[pr_code_suggestions]
code_suggestions_self_review_text = "... (your text here) ..."
```

<img src="/img/self_review_1.webp" alt="self_review_1" width="512" />

:::note[复选框只是视觉标记]

PR-Agent 会渲染该复选框，但不会对勾选做出反应。拉取请求作者点击它时，不会折叠任何内容，也不会添加批准。
:::

### 会生成多少条代码建议？

PR-Agent 使用动态策略，根据拉取请求（PR）的大小生成代码建议。工作方式如下：

#### 1. 对大型拉取请求分块

- PR-Agent 把大型拉取请求分成 “chunks”。
- 每个分块最多包含 `config.max_model_tokens` 个令牌（默认：32,000）。

#### 2. 生成建议

- 对每个分块，PR-Agent 最多生成 `pr_code_suggestions.num_code_suggestions_per_chunk` 条建议（默认：3）。
- 为了限制大型或已分块拉取请求的输出，把 `pr_code_suggestions.max_suggestions_per_file` 设为正整数。
  所有分块合并后，每个文件保留得分最高的建议；平局时保持原有顺序。
  摘要输出（包括未发布的摘要）会在应用正数上限之前，跳过行位置无法解析的建议。
  行内输出保持其现有的选择和回退行为。
  默认值 `0` 禁用此上限。

这种方法有两个主要好处：

- 可扩展性：建议数量随拉取请求大小伸缩，而不是固定不变。
- 质量：通过处理较小的分块，AI 可以保持更高质量的建议，因为更大的上下文往往会降低 AI 表现。

注意：分块主要与大型拉取请求相关。对于大多数拉取请求（最多 600 行代码），PR-Agent 能够在一次调用中处理全部代码。

分块运行期间，动画评论 `Work in progress ...` 会就地编辑，带上
已经分析的分块数，例如 `analyzed 2 of 3 chunks`，当分块放弃时还会加上 `... 1 chunk
failed`。更新需要 `config.publish_output_progress`，以及
同时支持编辑和删除评论的提供方，因此单分块运行和纯 diff
提供方会保留冻结的占位符。自动命令不发布进度评论，但在启用
`github.publish_as_check_run` 时，其进行中的 check run 会显示相同的分块计数。
回退模型会在开始之前恢复
占位符，并且每一轮重试都会计入总数，因此可见计数
既不会倒退，也不会过早停止。然后该评论会照常编辑成最终建议。

## 恢复部分失败的分析

部分失败的分析会自动对在其他分块成功之后抛出异常的分块，尝试剩余已配置的
`config.fallback_models`，除 `config.fallback_models` 本身外无需额外配置。
成功的预测会按原有顺序保留。恢复按模型逐个进行，
在前一批次结束后进行，并在已配置时使用匹配的 `openai.fallback_deployments`，
同时遵循该次调用的有效回退链，包括由
[模型路由](../usage-guide/changing_a_model.md#routing-small-pull-requests-to-a-cheaper-model)选择的主模型。
至少恢复了一个分块的回退模型会在运行
细节中标记为回退，因此已发布的运行行仍报告主模型，而粘性回退标志
保持设置。

在工具层面，每个剩余模型对仍然失败的分块最多尝试一次；模型
处理器现有的重试和自我反思调用可以增加提供方请求。完整
生成提示放不进某个回退模型令牌预算的分块会对该模型跳过，而不会
截断其上下文；预留余量遵循 AI 处理器将
实际为该模型请求的输出配额（`config.max_output_tokens` 及相关控制），当没有暴露具体限制时回退到
固定的软阈值。之后，更大的模型仍然可以恢复
它。耗尽的失败仍留在覆盖范围提示中。取消会向外传播，而不是开始
另一次重试。

这是同一次调用内的恢复，而不是跨命令的持久续跑。完全失败的初始
批次仍使用现有的整批回退。合法的空建议是成功结果；
被现有 YAML 解析器拒绝的响应保留其现有的解析失败行为。
含糊的重复模型/部署对会跳过部分恢复，而不是重新开始这条链。

## 理解 AI 代码建议 {#understanding-ai-code-suggestions}

- **AI 的局限：** 代码 AI 模型越来越好，但并非完美。不是所有建议都完美，用户不应自动接受全部建议。需要批判性阅读和判断。AI 的错误很少见，但可能发生，而且人类通常很容易发现它们。
- **建议的目的：**
    - **自我反思：** 建议旨在让开发者*自我反思*并改进自己的拉取请求。这个过程可以帮助发现盲点、找出遗漏的边界情况，并提高代码可读性和一致性。即使某条具体代码建议不合适，它指出的底层问题也常常揭示出值得注意的重要事项。
    - **缺陷检测：** 建议还会对分析期间可能识别出的*关键缺陷*发出警报。这提供了额外的安全网，在问题进入生产之前抓住潜在问题。只落实你认为对具体上下文有价值的建议完全可以接受。
- **层次结构：** 以结构化的层次表格呈现建议，使用户能够*快速*理解它们，并决定哪些相关、哪些不相关。
- **自定义：** 为了引导模型给出更符合项目具体需求的建议，建议使用 [`extra_instructions`](./improve.mdx#extra-instructions-and-best-practices) 和 [`best practices`](./improve.mdx#best-practices) 字段。
- **模型选择：** 对于特定编程语言或用例，某些模型可能比其他模型表现更好。
