## 先看它替你做哪一段

Gitee PR-Agent 是审核工厂的核心机。它只做中间的「取证」：阅读一张 Gitee 拉取请求，把证据写成中文评论。它不会替负责人决定能不能合并，也不会自己按下合并按钮。

<img src="/img/factory-flow-zh.svg" alt="审核分成四段。绿色的取证由 Gitee PR-Agent 完成，其余三段由人完成。" />

| 你看到的词 | 它的意思 | 谁来做 |
|---|---|---|
| 拉取请求 | Gitee 上一份等待合并的改动 | 提出人已经建好 |
| 取证 | 把改动、风险和建议写成评论 | 核心机 |
| 放行 / 退回 / 等待 | 最终判定的三个词 | 负责人 |
| 汇入 | 把这张请求合并进目标分支 | 有权限的人在 Gitee 上点击 |

## 第一次使用，按这六步

<img src="/img/first-run-zh.svg" alt="第一次使用按六步进行：复制地址、收集三项信息、运行命令、查看评论、阅读证据、写下判定。" />

### 1. 复制拉取请求地址

打开 Gitee 上要审查的页面，复制浏览器顶部的完整地址。普通仓库和企业仓库都可以：

```text
https://gitee.com/owner/repo/pulls/7
https://e.gitee.com/企业名/repos/owner/repo/pulls/7
```

### 2. 向同事收集三样东西

| 页面上的名字 | 向同事要什么 | 填到哪里 |
|---|---|---|
| 模型密钥 | 一串以 `sk-` 开头的文字 | `OPENAI__KEY` |
| 模型地址 | 以 `https://` 开头、通常以 `/v1` 结尾 | `OPENAI__API_BASE` |
| Gitee 令牌 | Gitee 个人访问令牌 | `GITEE__PERSONAL_ACCESS_TOKEN` |

这三样都是密钥。只贴进自己的终端，不要发到聊天群，也不要写进文档。

### 3. 填空并回车

电脑需要先安装 Docker。把尖括号和里面的说明换成真实内容，地址也换成第 1 步复制的地址：

```bash
docker run --rm -it \
  -e OPENAI__KEY=<模型密钥> \
  -e OPENAI__API_BASE=<模型地址> \
  -e CONFIG__GIT_PROVIDER=gitee \
  -e GITEE__PERSONAL_ACCESS_TOKEN=<Gitee 令牌> \
  ecloud-tcr.tencentcloudcr.com/ecloud_project/pr-agent:latest \
  --pr_url <第 1 步复制的地址> review
```

终端开始滚动文字，表示机器正在取证。不要关闭窗口。

### 4. 回到 Gitee 看评论

完成后，刷新拉取请求页面。评论区会出现 **PR 审查指南**。它包含审查工作量、是否有测试、安全问题和建议重点。评论只是证据，不是合并许可。

### 5. 需要代码建议时再跑一次

把上面命令最后的 `review` 改成 `improve`，再回车一次。页面会出现 **PR 代码建议**。建议停留在评论里，机器不能直接改仓库代码。

### 6. 负责人写下判定

在拉取请求里评论其中一个命令：

```text
/verdict 放行
/verdict 退回
/verdict 等待
```

然后再评论 `/merge-check`。只有“放行”且提交号没变时，页面才会写“可以由人合并”。最后仍要有权限的人在 Gitee 上点击合并。审查评论里的“批准”不是判定。

提出人也可以先评论 `/intake 新业务 这里写原话`。四个意图是 `新业务`、`旧版迭代`、`新版升级`、`双线`。写“双线”后，审查会要求先拆成两张请求。
