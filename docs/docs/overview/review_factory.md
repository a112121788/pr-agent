# 审核工厂是一套代理系统

审核工厂不是一个会说话的机器人包办全部工作。它是一组权限分开的代理：每个代理只完成一段，再把记录交给下一段。Gitee PR-Agent 是其中的取证代理，也是这套系统的核心机。

<img src="/img/factory-flow-zh.svg" alt="四段从左到右排列。只有取证段由 Gitee PR-Agent 完成。" />

评论区里的「可以合」想同时充当受理、取证、判定和汇入。它没有版本线，没有提交号，也不是「放行」「退回」「等待」之一，所以四段都没有完成。

## 五个代理

| 代理 | 执行者 | 只允许做的事 | 明确不做的事 |
|---|---|---|---|
| 受理代理 | 提出人，使用 `/intake` | 记录四个意图之一，并原样保存后面的话 | 改写原话，写判定 |
| 规则代理 | 程序规则，不调用模型 | 发现 `<a>`、`<button>`、缺失 spec，或显式双线时写下阻塞项 | 给出放行 |
| 取证代理 | openai-codex SDK，只读沙箱 | 阅读当前 diff，写出绑定提交号的中文证据 | 修改仓库、发布评论或合并 |
| 判定代理 | 负责人，使用 `/verdict` | 对当前提交写下「放行」「退回」或「等待」 | 合并代码 |
| 汇入检查代理 | `/merge-check` | 对照最新判定和当前提交号 | 调用 Gitee 合并接口 |

取证代理内部还可以继续分工：`/describe` 写变更包，`/review` 写风险和规则结果，`/improve` 写代码建议，`/ask` 回答一个问题。它们都停在取证，不继承判定权。

## 交接

代理之间不靠聊天记忆交接，只靠拉取请求上的评论交接。

1. 受理代理先写下意图、目标分支和提交号。没有这张记录，取证代理不知道该用哪一份清单。
2. 取证代理写完证据后停止。评论开头的提交号就是交接物。
3. 判定代理看见证据后，另写一条判定记录。审查正文里的「批准」不能自动变成这条记录。
4. 汇入检查代理只在「判定是放行，且提交号仍是当前提交」时写出「可以由人合并」。退回、等待或提交号变化时写出「不能汇入」。
5. 驾驶舱不自动开审。登记仓库后，点「批量审查」，或在每张拉取请求上点「审查」。正在审查的标成审查中，同一张不能同时再审一次。闸门允许时自己合并。退回、等待、提交变化，以及已经写明的双线，留给人处理。用法见 [驾驶舱](../usage-guide/dashboard.md)。

作者和新提交出现后，提交号变化。旧证据和旧判定一起失效，取证代理和判定代理都要重做。

## 共享状态

这套系统没有单独的数据库。评论 `/status` 会读取共享状态，并直接写出当前段和下一步。共享状态就是 Gitee 评论区里的四类记录：

- `## 受理记录`
- 以 `提交号：` 开头的审查或建议
- `## 判定记录`
- `## 汇入检查`

读者按这四个标题就能看出单子停在哪一段，不必重读整份 diff。

## 规则代理先于模型

有三类错误不交给模型判断：

- HTML 或 JavaScript 新增了 `<a>`、`<button>`。
- 功能变更没有更新 `specs/` 或 `openspecs/`。
- 受理记录明确写了「双线」。

规则代理把它们写成阻塞项。普通描述里出现「同时改旧字段和新汇总」，不会被猜成双线；只有 `/intake 双线` 才触发。
