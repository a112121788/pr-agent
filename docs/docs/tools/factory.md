title: "审核记录"

这些命令是审核工厂的交接协议。每个命令只代表一个代理，评论就是交给下一段的状态。Gitee PR-Agent 不把几段并成一句「可以合」。

## 受理

提出人写明这张请求属于哪一类：

```text
/intake 新业务 增加出科确认
```

只接受 `新业务`、`旧版迭代`、`新版升级`、`双线`。后面的文字原样保存。非法意图不会发布评论。

## 取证

`/review` 和 `/improve` 的最终评论以当前提交号开头：

```text
提交号：abc123456789
```

提交变化后，旧评论不再代表当前改动。

## 判定

负责人只写三个词之一：

```text
/verdict 放行
/verdict 退回
/verdict 等待
```

评论包含判定、提交号和判定人。审查正文里的“批准”“请求修改”“仅评论”不是判定。

## 汇入检查

```text
/merge-check
```

只有最新判定是“放行”，并且它的提交号等于当前提交时，结果才是“可以由人合并”。缺少判定、提交已变化、判定为退回或等待时，结果都是“不能汇入”。

`/merge-check` 这条命令本身不合并。驾驶舱不自动开审。人在每张拉取请求上点审查；正在审查的标成审查中，同一张不能同时再审一次。不先规划意图。它只在当前提交已有放行、且不是双线时调用 Gitee 合并接口。退回、等待或提交已变化时留给人抽查。抽查发现的问题用来改规则和环境。

## 当前状态

评论 `/status`。它只读取上面的记录，不调用模型，也不改任何记录。

```text
## 工厂状态

- 当前段：判定
- 下一步：负责人运行 /verdict
```

没有受理时停在受理；没有当前提交的证据时停在取证；证据已齐但没有当前判定时停在判定。只有当前判定是“放行”时，当前段才是汇入。审查正文里的“批准”不会让状态跳到汇入。

## 双线

`/intake 双线 ...` 之后，`/review` 会增加一条阻塞项：先拆成两张拉取请求。普通描述里出现“同时改旧字段和新汇总”不会被自动猜成双线。
